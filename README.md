# Olist E-Commerce Analysis

End-to-end BI portfolio project built from the **Brazilian E-Commerce
Public Dataset by Olist**.

**Workflow:** CSV → PostgreSQL → Data Quality → Relational Modeling →
SQL Analysis → Power BI → Validation

The objective was not only to build a dashboard, but to create a
reproducible analytical model, investigate source-data quality, define
business metrics explicitly, and validate the final Power BI results
against PostgreSQL.

## Business Questions

The analysis was designed to answer six practical questions:

1.  How much product revenue was generated by delivered orders?
2.  How many orders were delivered?
3.  What was the average order value?
4.  How many unique customers purchased?
5.  Which product categories and Brazilian states contributed the most?
6.  How did sales and delivery performance behave over time?

## Dataset

The source contains nine CSV files.

  -------------------------------------------------------------------------
  Source table                          Grain / purpose
  ------------------------------------- -----------------------------------
  `customers`                           Customer record associated with an
                                        order

  `orders`                              One row per order

  `order_items`                         Product/seller item within an order

  `products`                            Product attributes

  `sellers`                             Seller attributes

  `order_payments`                      Payment records associated with
                                        orders

  `order_reviews`                       Reviews associated with orders

  `geolocation`                         ZIP-level geographic observations

  `product_category_name_translation`   Portuguese-to-English category
                                        lookup
  -------------------------------------------------------------------------

One important distinction discovered during profiling is that
`customer_id` identifies the customer record associated with an order,
while `customer_unique_id` represents the logical customer across
purchases. Unique-customer metrics therefore use `customer_unique_id`.

## Project Workflow

### 1. Raw Data Inspection

Each CSV was inspected before constraints were finalized. The analysis
established:

-   row grain;
-   candidate primary keys;
-   foreign keys;
-   nullability;
-   cardinality;
-   PostgreSQL data types;
-   duplicate behavior.

This prevented assumptions about uniqueness or relationships from being
encoded directly into the database.

### 2. Relational Modeling

The main analytical path is:

``` text
product_category_name_translation
              1
              │
              *
           products
              1
              │
              *
         order_items
              *
              │
              1
            orders
              │
              1
          customers
```

`orders` also relates to `order_payments` and `order_reviews`.
`geolocation_clean` is used as an analytical geographic lookup.

### 3. Data Quality and Constraint Validation

Primary keys and relationships were tested against the source data
before being enforced. Several assumptions that appeared reasonable
initially did not hold when validated.

### 4. SQL Business Analysis

After the relational model was established, SQL was used to define and
validate revenue, order, customer, category, geography and logistics
metrics.

### 5. Power BI

The validated analytical tables were imported into Power BI, a dedicated
date dimension was added, reusable DAX measures were created, and the
dashboard results were compared with PostgreSQL.

## Data Quality Findings & Technical Decisions

### `customer_id` vs `customer_unique_id`

`customers` contains:

-   **99,441 rows**
-   **99,441 distinct `customer_id` values**
-   **96,096 distinct `customer_unique_id` values**

`customer_id` is therefore used for the order relationship, while
`customer_unique_id` is used when measuring actual unique customers.

### `review_id` Was Not Globally Unique

Validation showed that `review_id` alone could not serve as the primary
key because duplicate values exist.

The pair:

``` text
(review_id, order_id)
```

was validated as unique and used as the composite primary key.

This demonstrates why candidate keys were tested against the source
rather than assumed from column names.

### Payments and Reviews Can Be One-to-Many

`order_payments` can contain multiple payment records for one order; one
order contained **29 payment records**.

The payment primary key was therefore modeled as:

``` text
(order_id, payment_sequential)
```

Reviews were also modeled as potentially one-to-many from orders.

This introduces a critical analytical risk: joining `order_items`,
`order_payments` and `order_reviews` directly can create **fan-out**,
multiplying rows and overstating aggregated values. Business queries
therefore use only the required tables at a compatible grain.

### Missing Product-Category Translation Keys

Two categories used by `products` were absent from the translation
lookup:

-   `portateis_cozinha_e_preparadores_de_alimentos`
-   `pc_gamer`

The missing Portuguese keys were inserted with a `NULL` English
translation rather than inventing values. This preserved referential
integrity without fabricating source data.

### Geolocation Required Cleaning

The raw geolocation source contained:

-   **1,000,163 rows**
-   **738,332 distinct complete rows**
-   **261,831 redundant duplicate rows** (\~26.18%)
-   **8,559 ZIP prefixes** associated with more than one city/state
    combination
-   **8 ZIP prefixes** associated with more than one state

Because ZIP prefix was not unique, it could not be used directly as a
primary key.

A new analytical table, `geolocation_clean`, was built by:

1.  counting city/state occurrences within each ZIP;
2.  ranking them with `ROW_NUMBER()`;
3.  retaining the most frequent city/state combination;
4.  calculating representative latitude/longitude from distinct
    coordinate pairs.

The result contained **19,015 rows and 19,015 unique ZIP prefixes**.

Geographic coverage was still incomplete:

-   **157 customer ZIP prefixes** were absent;
-   **7 seller ZIP prefixes** were absent.

For this reason, PostgreSQL foreign keys from customers/sellers to
`geolocation_clean` were intentionally not enforced. Geography remains
an analytical lookup so valid business records are not discarded because
of incomplete geographic coverage.

### Temporal Coverage Was Irregular at the Edges

Order timestamps span:

-   **Minimum:** 2016-09-04 21:15:19
-   **Maximum:** 2018-10-17 17:30:18

However, 2016 is sparse and September/October 2018 contain very few
orders and are not comparable with normal full months.

The complete data remains available in the model, but the dashboard
trend uses:

**January 2017 -- August 2018**

This prevents incomplete edge-period coverage from being interpreted as
a genuine collapse in business activity.

## Business Definitions

### Revenue

For this project:

``` text
Revenue = SUM(order_items.price)
          for orders where order_status = 'delivered'
```

This metric represents **product revenue from delivered orders**. It is
not intended to represent formal accounting revenue recognition.

Freight is excluded.

### Delivered Orders

Count of orders where:

``` text
order_status = 'delivered'
```

### Average Order Value

Revenue divided by delivered orders, equivalent to aggregating item
prices to order grain and then calculating the average order total.

### Unique Customers

Distinct `customer_unique_id` values associated with delivered orders.

### Average Delivery Time

Average elapsed time between purchase timestamp and customer delivery
timestamp for delivered orders.

### Late Delivery Rate

Percentage of delivered orders where:

``` text
order_delivered_customer_date > order_estimated_delivery_date
```

## Power BI Model

The Power BI MVP imports:

-   `customers`
-   `orders`
-   `order_items`
-   `products`
-   `product_category_name_translation`
-   `geolocation_clean`

A dedicated `DimDate` table was created for temporal analysis. A
date-only `Purchase Date` column was derived from
`order_purchase_timestamp` and related to `DimDate[Date]`.

This allows the date dimension to filter orders, which then propagates
through the analytical model and recalculates reusable measures such as
Revenue.

### Core DAX Measures

#### Revenue

``` dax
Revenue =
CALCULATE(
    SUM('public order_items'[price]),
    'public orders'[order_status] = "delivered"
)
```

#### Delivered Orders

``` dax
Delivered Orders =
CALCULATE(
    COUNTROWS('public orders'),
    'public orders'[order_status] = "delivered"
)
```

#### Average Order Value

``` dax
Average Order Value =
DIVIDE(
    [Revenue],
    [Delivered Orders]
)
```

#### Unique Customers

``` dax
Unique Customers =
CALCULATE(
    DISTINCTCOUNT('public customers'[customer_unique_id]),
    'public orders'[order_status] = "delivered"
)
```

#### Average Delivery Days

``` dax
Average Delivery Days =
CALCULATE(
    AVERAGEX(
        'public orders',
        DATEDIFF(
            'public orders'[order_purchase_timestamp],
            'public orders'[order_delivered_customer_date],
            SECOND
        ) / 86400
    ),
    'public orders'[order_status] = "delivered"
)
```

#### Late Delivery Rate

``` dax
Late Delivery Rate =
DIVIDE(
    CALCULATE(
        COUNTROWS('public orders'),
        FILTER(
            'public orders',
            'public orders'[order_status] = "delivered"
                && 'public orders'[order_delivered_customer_date]
                   > 'public orders'[order_estimated_delivery_date]
        )
    ),
    [Delivered Orders]
)
```

Display-only measures were used where necessary to prevent automatic KPI
abbreviation in the Power BI card visual. The underlying numeric
measures remain unchanged for calculations.

## How to Reproduce

1.  Download the Olist Brazilian E-Commerce dataset from its original
    source.
2.  Create a PostgreSQL database named `olist_ecommerce`.
3.  Create the relational tables using `sql/01_create_tables.sql`.
4.  Import the corresponding CSV files.
5.  Run `sql/02_data_quality_checks.sql` to reproduce the principal
    profiling checks.
6.  Build `geolocation_clean` using `sql/03_geolocation_clean.sql`.
7.  Apply the validated constraints with `sql/04_constraints.sql`.
8.  Run the business queries in `sql/05_business_analysis.sql`.
9.  Connect Power BI Desktop to PostgreSQL in **Import** mode.
10. Build the semantic model and DAX measures documented above.
11. Use January 2017 through August 2018 for the monthly trend visual.
12. Compare the Power BI KPIs against the validated SQL results.

> Raw Olist CSV files are intentionally not included in this repository.

## Key Takeaway

Dashboard development begins before Power BI.

Several apparently reasonable assumptions --- unique review IDs, unique
ZIP codes, complete translation coverage, one-to-one payment behavior
and uniform temporal coverage --- did not hold when tested.

Profiling and modeling these issues in PostgreSQL first produced a
cleaner and more defensible analytical layer, while making the final
Power BI results easier to validate, reproduce and explain.
